# ADR 0004 — PAdES signatures in the PDFs, with a two-tier document-control key

- **Status:** Accepted
- **Date:** 2026-08

## Context

Printed or emailed copies of policies are uncontrolled; readers need a way to tell an authentic
release from an edited copy. Options considered: a detached GPG signature per file (invisible to a
PDF reader, needs tooling), a hash manifest only (integrity, no origin), or a signature embedded
in the PDF that readers display natively.

## Decision

Every rendered PDF is signed with a **PAdES signature** (pyHanko) and a visible stamp on the
cover page; `dist/SHA256SUMS` lists every output, and a release attaches a build-provenance
attestation. The signing identity is a **two-tier PKI**: an issuing CA (the trust anchor, a public
PEM) and a signing certificate, both generated by `isms keygen` and stored as a CI secret
(PKCS#12, base64). When no key is configured — forks, local builds — an **ephemeral key whose
common name reads "UNTRUSTED DEVELOPMENT KEY"** is used, so the pipeline always runs but a dev
build can never be mistaken for a controlled copy. `isms verify` validates integrity, whole-file
coverage and the chain to the anchor.

## Consequences

- **Readers see the signature** in any PDF viewer; auditors verify with one command or by importing
  the trust anchor.
- **Forks and pull requests exercise the full pipeline** without access to secrets.
- **Trade-off.** The key is self-managed, not publicly trusted: viewers show "unknown trust" until
  the anchor is imported, and there is no timestamp-authority countersignature by default (a
  `--tsa-url` option exists). Private keys never touch the repository; `.gitignore` and the
  `detect-private-key` hook guard against it.
